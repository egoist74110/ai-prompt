# 交叉审查（Cross-Review：不同高级模型互审代码）

实现方与审查方**不能是同一个运行时**。跨厂商审查的价值是抓同一家模型的共同盲区（相似训练偏好、对同一框架的相同理解、同一种"想当然"）。本文件是工作流：何时派、派给谁、怎么派、怎么收。

**不维护模型名列表**：各运行时用什么模型由运行时自己决定（模型更新很快，列表必然过期）；只按运行时配对。

## 何时用

自检通过后、交付前必须做交叉审查：

- 用户明确要求审查 / 交叉审查
- 涉及安全（鉴权、注入、密钥、权限、脱敏）、关键数据流（多步写、事务、资金/库存类）、跨模块重构、上线就绪
- 高模自检后仍有不确定项

豁免（自检通过即交付）：trivial 修复、纯配置、一行改动、无外部副作用的单文件局部逻辑。

## 配对规则（固定单审查，就开一个；实现方跳过自己，按 Claude → codex → agy 顺序取下一个；只看运行时，不看模型名）

| 实现方 | 审查方（就一个） |
|---|---|
| Claude Code | codex |
| Codex | Claude Code |
| agy（Antigravity） | Claude Code |
| DSH / 本地模型 | Claude Code |

## 怎么派（headless 调用，在目标仓库目录里执行）

- Claude Code：`claude -p "<审查请求>"`
- Codex：`codex exec "<审查请求>"`
- agy：`agy -p "<审查请求>"`

审查方按它自己的运行时入口读中央提示词（router），身份是**审查者**：只读 + 只出意见，不改码。

## 审查请求格式（必须具体，参照 `models/scout.md` 的执行请求纪律）

请求里包含：

1. **改动范围**：文件列表或 `git diff`（大改动按模块分批，不要整个 diff 一把梭）。
2. **背景**：一句话说明在实现什么需求/工单。
3. **审查清单**：正确性与边界条件；并发与失败路径；安全（鉴权/注入/密钥）；与现有代码风格与架构的一致性；资源生命周期（连接/句柄/订阅的清理）。
4. **输出要求**：每条问题给 `file:line` + 问题 + 严重度（blocker / major / minor）+ 具体建议；结尾给结论：**通过 / 修 minor 后可过 / 需返工**。
5. **禁令**：审查方不得直接重写整段代码（用户要求除外）；只审给定范围；无法确认的事实标 unknown，不猜；风格吹毛求疵不得标 blocker。

## 收反馈（实现方）

- 按 `receiving-code-review` skill 执行：逐条核实（读原文 / 跑验证），不盲目同意，不表演性认同；不同意要给出证据说明。
- blocker / major 必须修复并复验；minor 可解释后保留（记进交付汇报）。
- 审查结论是参考输入，最终由实现方高模 + 用户拍板。

## Guardrails

- 审查方结论是参考输入，最终交付决定权在实现方高模 + 用户。
- 交叉审查不是每次小改动的强制流程（成本问题），见「何时用」。
- headless 调用继承该运行时自己的权限与配置；不要为了审查方便给额外权限。
