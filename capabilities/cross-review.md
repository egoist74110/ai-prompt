# 交叉审查（Cross-Review：不同高级模型互审代码）

实现方与审查方**不能是同一个运行时**。跨厂商审查的价值是抓同一家模型的共同盲区（相似训练偏好、对同一框架的相同理解、同一种"想当然"）。本文件是工作流：何时派、派给谁、怎么派、怎么收。

**不维护模型名列表**：各运行时用什么模型由运行时自己决定（模型更新很快，列表必然过期）；只按运行时配对。

## 先判身份（递归终止条件，最重要）

本文件有两种读者，适用条款完全不同。**判据是当前请求交给你的职责，不是启动方式**——headless 命令（`claude -p` / `codex exec` / `agy -p`）既能派实现也能派审查，光看命令判不出身份。

- **实现方**：当前请求要你写/改代码并交付 → 按下面「何时用 / 配对规则 / 怎么派」执行。
- **审查方 / 验证方**：当前请求明确把你限定为"只读 + 只出意见 / 不改代码 / 审查或验证某段已有改动" → 产出**至少**满足「审查请求格式」第 4 条，请求里额外要求的范围、清单、字段照做，然后结束。

**审查方绝对不得再派交叉审查。** 审查请求里必然带"审查"二字，若审查方也执行「何时用」的第一条，就会 Claude→codex→Claude 层层递归派发，成本翻倍且可能来回弹。`models/high.md` 的 Cross-Review Gate 对审查方同样不适用。

身份**按阶段重判**：审查完用户让你动手修 → 从那一刻起是实现方；实现完自己复看自己的改动 → 那是自检，不是交叉审查，不能拿来满足"不同运行时"的前提。详见 `models/high.md` 的 Identity Gate。

## 何时用（**仅实现方**；审查方见上一节）

自检通过后、交付前，按两条路径判断，**门槛不同**：

1. **用户明确要求审查**（说"审查"/"帮我审查"/"交叉审查"/"审一下"等任何明确审查意图）
   → **立即执行本文件完整流程，不用二次确认，不用问"要不要交叉审查"**。无论改动大小都审查，豁免条款不适用。
2. **用户没提，但改动命中高风险面**——安全（鉴权、注入、密钥、权限、脱敏）、关键数据流（多步写、事务、资金/库存类）、跨模块重构、上线就绪，或高模自检后仍有不确定项
   → **先一句话告知用户"这块命中 X，建议派 <运行时> 审查 <范围>"，等确认再派**。派审查会拉起另一个 AI 运行时消耗额度，是用户看不见的昂贵操作，不自作主张。用户说不用就直接交付，把风险点写进汇报。
   → **非交互场景**（headless，没有下一轮可等）：不得擅自派发，也不要干等；把"待确认：建议派 X 审查 Y，原因 Z"写进本次输出即结束。原请求已明确授权审查的视为已确认，直接派。

豁免（连告知都不需要，自检通过即交付）：trivial 修复、纯配置、一行改动、无外部副作用的单文件局部逻辑。

## 配对规则（优先级，单审查就开一个；只看运行时，不看模型名）

优先级顺序：**Claude > codex > agy**。

规则：审查方 = 这个优先级序列里、**第一个不等于实现方**的运行时。实现方不在序列里（如 DSH / 本地模型）时，直接取序列最高 = Claude。

推导出来：

| 实现方 | 审查方 |
|---|---|
| Claude Code | codex（跳过自己，取下一个） |
| Codex | Claude Code（最高） |
| agy（Antigravity） | Claude Code（最高） |
| DSH / 本地模型（不在序列） | Claude Code（最高） |

## 怎么派（headless 调用，在目标仓库目录里执行）

- Claude Code：`claude -p "<审查请求>"`
- Codex：`codex exec "<审查请求>"`
- agy：`agy -p "<审查请求>"`（**不要加 `--mode plan`**——plan 模式连读文件都要交互确认，headless 下全部自动拒绝，直接"没有输出"退出；也**不要用 `--dangerously-skip-permissions`**，官方明确警告会放行全部写文件+命令，且会被上游运行时的高危分类器拦截）

agy 的 headless 权限（已按官方文档配好）：agy 的 print 模式**不会**自动放行工作区文件读取（交互式会话才会），必须在 `~/.gemini/antigravity-cli/settings.json` 的 `permissions.allow` 里有 scoped 规则——本机已配 `read_file(/Users/wesker)`。

两个前置条件，不满足就会"没有输出"退出，别当成审查通过：

- 该文件的 `trustedWorkspaces` 必须包含目标仓库路径（本机当前只列了 5 个目录），否则 headless 直接拒绝。
- 审查方如需跑特定命令（如 `git diff`、跑测试），需要细粒度 `command(git diff)` 类规则。

**改这个文件（或任何运行时的权限配置）等同于扩大 AI 的访问面，必须先向用户说明改什么、为什么、影响范围，得到确认后再改**——同 `router.md` Capability Loading 的确认纪律。绝不为了"审查方便"直接放大权限，更不用 `--dangerously-skip-permissions`。

**审查方无输出 / 调用失败时**：不要静默当成"审查通过"。先按上面两条查前置条件，仍不行就在交付汇报里如实写明"交叉审查未能执行，原因 X"，由用户决定是换运行时重派还是接受自检结果交付。

审查方按它自己的运行时入口读中央提示词（router），身份是**审查者**：只读 + 只出意见，不改码。

## 审查请求格式（必须具体，参照 `models/scout.md` 的执行请求纪律）

请求里包含：

1. **改动范围**：文件列表或 `git diff`（大改动按模块分批，不要整个 diff 一把梭）。**文件一律用绝对路径**——agy 的文件解析不一定跟随调用方 cwd（实测：让它读"当前目录的 README.md"，它读到了别的项目的同名文件）；相对路径只会在调用方自己的目录里可靠。
2. **背景**：一句话说明在实现什么需求/工单。
3. **审查清单**：正确性与边界条件；并发与失败路径；安全（鉴权/注入/密钥）；与现有代码风格与架构的一致性；资源生命周期（连接/句柄/订阅的清理）。
4. **输出要求**：每条问题给 `file:line` + 问题 + 严重度（blocker / major / minor）+ 具体建议；结尾给结论：**通过 / 修 minor 后可过 / 需返工**。
5. **禁令**：审查方不得直接重写整段代码（用户要求除外）；只审给定范围；无法确认的事实标 unknown，不猜；风格吹毛求疵不得标 blocker。

## 收反馈（实现方）

- 按 `receiving-code-review` skill 执行：逐条核实（读原文 / 跑验证），不盲目同意，不表演性认同；不同意要给出证据说明。
- blocker / major 必须修复并复验；minor 可解释后保留（记进交付汇报）。
- 审查结论是参考输入，最终由实现方高模 + 用户拍板。

## 验证交接（测到死验证：把现成提示词发给用户）

审查结束后，凡是**静态读码无法确认、需要实际跑起来验证**的项（跑测试、端到端、边界/失败路径复现、性能），实现方在交付汇报里输出一段**可直接粘贴的验证提示词**（markdown 代码块），用户会把它带到 DSH 里调用本地模型做"测到死"验证。

**提示词由实现方高模自己写，不套固定模板**——高模握有完整上下文（审查意见、代码、工单验收标准、环境细节），它产出的测试用例设计一定比模板好（能写出"这个 key 可以直接改来构造前置状态"、"这个入口是 tab 页不是独立路由"这种只有它知道的东西）。但以下硬要求必须满足——这些是本地模型猜不到、接收方流程依赖的：

1. **自包含**：本地模型看不到当前会话。必须写进提示词：仓库绝对路径 + 分支/commit、改动范围（文件清单）、背景（工单/需求一句话 + 上一轮审查修了什么）、环境入口（启动命令 + 精确入口路径，含容易踩的细节如"这是 tab 页，必须带 ?name=xxx"）、权限要求（缺权限时找有权限的测试账号，**不要绕过权限判断硬测**）、**前置状态构造方法**（能手动改 localStorage/数据库/配置直接造状态的，给出 key/字段，不要每次都靠真实业务流攒数据）。
2. **测到死**：明确要求不只验 happy path，逐条问"如果我是想搞崩它的人，我会怎么戳"，并按场景列手段（快速连点、中途改值、脏数据、断网/超时、并发多开等）。
3. **回归项优先**：本轮审查揪出来、已修复的项要显式标记（如【回归重点】）并优先测，确认是**真的修好了、不是治标不治本**。
4. **报告格式**：每条问题 = 现象 + 复现步骤 + 期望 vs 实际 + 严重度（blocker/major/minor）+ 涉及文件（file:line 能定位就给）；结尾整体结论三档：**通过 / 修 minor 后可过 / 需返工**。
5. **身份边界**：验证执行者——只收集事实、如实报告，不改代码、不扩范围；跑不了的项明确说明原因，不编造结果。
6. **已知非缺陷**（如有）：已确认的误报/噪声（如仓库里某个 lint 插件的已知解析 bug）列出来，要求不要重复上报，避免浪费验证轮次。

用户把本地模型跑完的结果拿回来后，实现方按 `receiving-code-review` 纪律逐条核对：失败项修掉复验，通过项才能算闭环。

## Guardrails

- 审查方结论是参考输入，最终交付决定权在实现方高模 + 用户。
- 交叉审查不是每次小改动的强制流程（成本问题），见「何时用」。
- headless 调用继承该运行时自己的权限与配置；不要为了审查方便给额外权限。
